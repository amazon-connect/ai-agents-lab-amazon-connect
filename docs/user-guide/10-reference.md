# Reference

## Test script YAML format

A test script defines a multi-turn conversation to be replayed by the Script Runner or Batch tester.

### Full example

```yaml
name: "Damaged item return flow"
turns:
  - customer: "I received a damaged item in my order"
  - customer: "My order number is 78234"
  - customer: "Yes, I'd like a full refund please"
  - customer: "My email is customer@example.com"
```

### Fields

| Field | Required | Description |
|-------|----------|-------------|
| `name` | Yes | A label for the script. Shown in the Testing page and in batch export filenames. |
| `turns` | Yes | An ordered array of conversation turns. |
| `turns[].customer` | Yes | The customer utterance to send for this turn. |
| `turns[].variations` | No | An array of alternative phrasings for this turn. Populated automatically by Generate variations. During batch runs, one utterance is selected at random per iteration from `[customer] + variations`. |

### With variations

After running Generate variations, turns gain a `variations` array:

```yaml
name: "Damaged item return flow"
turns:
  - customer: "I received a damaged item in my order"
    variations:
      - "My package arrived damaged"
      - "I got a broken item"
      - "The item I ordered came in damaged condition"
  - customer: "My order number is 78234"
    variations:
      - "Order 78234"
      - "It's order number 78234"
```

## Evaluation forms

> The evaluation workflow now uses structured Amazon Connect evaluation forms instead of YAML reference files. Evaluation forms are generated directly from the Testing page by clicking **⋮ → Create evaluation form** after a successful chat conversation. See [Manual Testing → Create evaluation form](./04-manual-testing.md#create-evaluation-form) for the full workflow.

## Glossary

| Term | Definition |
|------|-----------|
| **Span** | A single unit of work in an AI agent execution trace: Invoke Agent, Inference, or Execute Tool. |
| **Invoke Agent** | The top-level span representing one complete agent turn — from receiving the customer message to producing a response. |
| **Inference** | A span representing a single LLM call to Amazon Bedrock within an agent turn. |
| **Execute Tool** | A span representing a tool invocation by the agent (e.g. a Lambda function, an API call). |
| **Evaluation form** | A structured Amazon Connect evaluation form with sections and questions. Generated from a successful conversation on the Testing page using "Create evaluation form". Deployed to Connect for automated gen-AI scoring. |
| **Hydration** | The process of fetching the real Contact Lens post-call transcript for each contact ID from the batch results. Required before evaluation can score a contact. |
| **Pass rate** | The percentage of evaluated contacts that received an overall passing score (≥ 90%). |
| **Verdict** | The evaluation outcome for a contact: pass (score ≥ 90%), partial (50–89%), or fail (< 50%). |
| **Justification** | The written rationale from Connect's gen-AI evaluator explaining how it answered a specific question, with references to the conversation transcript. |
| **p50** | The median iteration duration in a batch run. Half of iterations completed faster than this. |
| **p95** | The 95th percentile iteration duration — 95% of iterations completed faster than this value. A high p95 relative to p50 indicates occasional slow outliers. |
| **Silence threshold** | The number of seconds of silence after the agent speaks before the voice test runner advances to the next customer turn. |
| **Settle duration** | The number of seconds the chat script runner waits after receiving an agent message before deciding the turn is complete and sending the next customer utterance. Allows time for multi-part agent responses to arrive. |
| **Variation** | An alternative phrasing for a customer utterance, generated by Bedrock to diversify batch test inputs. |
| **Infrastructure setup** | The one-time provisioning of a Lex bot and Connect contact flow required before automated testing can run. |

## Troubleshooting

### `Access Denied: kms:GenerateDataKey` when opening the Testing page

**Symptom:** Navigating to the Testing page shows an Access Denied error referencing `kms:GenerateDataKey`, even though the user has full admin permissions on the account.

**Cause:** The Amazon Connect AI Agents assistant is configured with a customer-managed KMS key (CMK) for encryption at rest. KMS uses dual authorization — both the caller's IAM policy *and* the key policy must allow access. If the CMK's key policy doesn't include the account root principal (`arn:aws:iam::<account>:root`), no IAM policy — not even `AdministratorAccess` — can authorize key usage.

This typically happens when:
- The assistant was created with a CMK whose key policy only grants access to the Wisdom/QConnect service, not to account principals
- The CMK is in a different account (cross-account key)

**Fix:** Add the account root (or the specific calling role) to the CMK's key policy:

```json
{
  "Sid": "Allow account principals via IAM",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::<account-id>:root" },
  "Action": ["kms:GenerateDataKey", "kms:Decrypt"],
  "Resource": "*"
}
```

**To identify the key:** call `GetAssistant` on the affected assistant — the response includes `serverSideEncryptionConfiguration` with the CMK ARN. Then inspect that key's policy in the KMS console.

### `No AWS accounts are assigned to your Identity Center user`

**Symptom:** Sign-in succeeds but the app displays "No AWS accounts are assigned to your Identity Center user."

**Cause:** The IDC user has no account + permission set assignment. Authentication (confirming identity) succeeded, but there are no AWS accounts the user is authorized to access, so the app cannot obtain temporary credentials.

**Fix:** In IAM Identity Center → Multi-account permissions → AWS accounts, assign the user (or their group) to the target account with a permission set that includes the required end-user permissions (see [Settings → Permissions](./09-settings.md)).
